# 旧项目批改能力与历史规则研究

研究日期：2026-11-25（北京时间）。对应研究票：[旧项目哪些能力可复用，哪些历史规则必须重新设计？](https://github.com/wozhendeshifwa/xuexitong_zuoye/issues/2)。

## 结论

旧项目可提供的是批改链路的实现候选与事故经验，不是一套可直接继承的新项目规格。优先评估复用逐题结构校验、提交版本检查、单人回传业务确认、回传后独立对账、断点处理与定稿保护。提交识别、参考答案抽取、评分政策、人工裁决门槛、提供商切换和状态恢复需要重新设计或验证。

本报告不替用户决定自动化程度、目标均分、分数区间、题型范围或产品形态。历史作业授权也不等于新项目授权。

## 方法、证据等级与边界

本报告由研究子代理依据 research 技能进行，读取旧项目本地一次资料与源码，未运行批改、模型调用、平台请求或旧项目测试，未读取学生材料、处理账本、学生名单或凭证。仅发布概括与代码定位，不复制学生数据。

旧项目根目录为 `C:\Users\27263\Desktop\作业批改`。下文 [S1] 等均指该目录下的源文件及行号或文档章节。证据来自本地工作副本，可能包含未提交变更；尝试读取旧项目 Git 状态受到访问限制，不能给出可信的整仓提交快照。不得把一次 Git 输出的其他仓库 HEAD 误当旧项目版本。

证据等级：

- **代码事实**：本次直接读到实现，证明存在这段逻辑，不证明线上运行正确或接口仍有效。
- **文档记录**：旧项目自身说明、事故记录或决策文档，未用原始平台材料独立重演验证。
- **测试定义**：读到测试名称与覆盖意图，未执行，不称“测试通过”。
- **研究判断**：依据上述证据提出的复用候选、缺口或设计影响，不冒充用户已决定的规则。

## 能力调查

| 环节 | 读到的事实 | 可复用候选与边界 |
| --- | --- | --- |
| 作业定位 | 通用入口有作业/名单元信息检查；不同作业又有独立脚本改写模块配置。[S1][S9][S10] | 身份校验思路可复用；全局模块变量与作业脚本不能直接充当多课程产品模型。 |
| 提交识别 | 名单收集以提交时间且学生作答区域第一个附件 objectid 为真提交；可以关闭附件检查，改为只看提交时间。[S2:33–81] | 学生作答区域边界必须保留；“有附件才提交”只适用历史附件型作业，不能用于纯文字等全部作业。 |
| 附件收集 | 收集器下载单个附件到 PDF 路径，交给 PDF 渲染器逐页转图；下载失败被隔离，但 PDF 打开与渲染在该 try 块外。[S3:10–31] | PDF 页图输入可复用；任意格式、多附件、坏 PDF 隔离、混合文字/图片尚未在此通路证明。 |
| 参考答案 | 评分器消费本地 JSON；load_key 识别“章-题号”格式并按题号合并答案。平台批阅页含参考答案属于文档记载。[S4:59–70][S11] | 参考答案结构化输入可借鉴；不能宣称已具备通用的学习通参考答案自动提取与更新能力。 |
| 逐题判分 | 提示提供题号、题型、分值、参考答案，输出分数/短转录/把握度；缺失参考答案会用提示文本代替而非停止。[S4:19–56] | 逐题输出结构可复用；缺答案是否允许评分、题干获取与答案版本必须显式决定。 |
| 结构校验 | 校验数组、题号覆盖、重复/多余题号、分数是否为 0/半分/满分。[S4:149–187] | 是明确可复用候选，但不验证学生证据是否真实、页图是否实际查看或评判是否正确。 |
| 重复判分 | 通用链路逐次调用、重试、三次合并，按题投票；分歧降为低把握。[S1:316–364][S4:207–241] | 采样、失败隔离与分歧留档可复用；多次一致不是正确率或视觉审核证明。 |
| 复核产物 | review.build 生成汇总及逐题工作表，并在同一次调用中调分、写 _final.json。[S5:42–121] | 展示逐题结果的思路可复用；函数名“复核”不能证明人工实际复核，报表生成与最终分写入耦合。 |
| 定稿/重交 | 通用批改跳过合法已定稿 JSON（force 可绕过）；增量流程通过指纹判断重交，并校验复核版本，保护已定稿结果。[S1:299–313][S6:19–80] | 定稿保护和版本核验应保留，但跨作业身份、答案/模型/政策版本需要更完整建模。 |
| 回传 | 通用 score 命令打印 HTTP 与响应后返回 0；增量 deliver 同时检查 HTTP 200 与 JSON status=true。[S1:519–536][S6:90–101] | 采用增量链路的业务确认思路；不能把通用命令退出成功等同平台写入成功。 |
| 对账 | compare_scores 检查名单、状态“完成”、分数、取整差异和平台多出的本地缺失记录；人工差异作为 mismatch 报出。[S1:117–177] | 独立读取平台结果后对账可复用；状态依赖字符串、字典折叠重复学号等输入假设仍需验证。 |
| 重试/完成 | 增量流程在写前重新检查当前提交，保留 upload_ack/auto_pending，核对平台模板后结束；完成需近期截止时间与待重做证据、版本/名单/定稿/对账一致。[S6:116–215] | 状态分层与证据门槛可复用；不等同完整事务恢复、自动回滚或通用多作业调度能力。 |

以上表格实现描述为“代码事实”；对复用及缺口的表述为“研究判断”。平台接口行为仅有文档与调用实现支持，未做当前线上验证。

## 已记录事故与实现差距

### 导入事故及守卫边界

旧项目文档和 emit.py 模块注释均记录：2026-10-17，手拼导入文件导致 87 名未交学生被写成 0 分并改变状态。接口文档说明导入按行写入、部分名单导入受限、找不到恢复未交入口。[S7:1–7][S11「写操作」「没有恢复未交」][S12「交代分产物」] 这是第一方文档事故记录，未经本次独立重演；不能推广为学习通永远不支持恢复。

emit.select_rows 检查分数范围、学号存在、选中行数与 scores 数量一致。它的入参没有独立的最新提交名单；“submitters”统计值实际为 len(scores)。因此守卫仅证明“输出人数 = 给分人数”，不能独立证明“给分人数 = 真实提交人数”。上游传入错误 score_map 时，此守卫本身不能辨认未提交者。[S7:29–62][S1:491–507]

**设计影响（研究判断）**：输出/回传资格需要独立来源、身份与提交版本验证，不能靠给分列表自证。批量导入方式是否保留，需要重新核对当前平台能力。

### 评分器局部规则不一致

提示要求选择题只能 0/满分；validate_items 却对所有题统一允许半分。因此“通过结构校验”不表示符合题型规则。[S4:35,53,175–186]

通用 merge_votes 使用 Counter.most_common(1)，没有对三次各异等无多数情况定义单独裁决状态；它以第一份样本为转录等字段基础，替换投票得分。因此合并分数与保留解释不一定源自同一份样本。[S4:230–240]

build_prompt 明确说缺作答给零、难辨低把握，未建立独立“不可读而暂停”状态；这不能自动获得后续某作业“不可读不得猜分”的保护。[S4:41,54][S8:25–30,35]

**设计影响（研究判断）**：题型规则、无多数裁决、不可读状态、证据与裁决对应关系都应成为显式决策，不把“三次投票”当完整质量保障。

### 提供商入口与声明发生分叉

第 4 章第一次入口安装 Codex 适配器；该适配器固定模型，使用安装的 Codex CLI，校验返回逐题结构。[S9:4–14][S13:10–54]

第 4 章第二次入口先将 config.load_vision 设为拒绝旧链路的 _codex_only，随后导入 qwen37_grading 并 install；后者又把 config.load_vision 与 judge.grade_images 设回 Qwen 实现。按这些源文件的顺序，早先拒绝旧链路的赋值会被覆盖。[S10:14–28][S8:48–63] 此判断为静态代码追踪，未执行；不能依据入口提示断言实际一定采用 Codex。

**设计影响（研究判断）**：模型选择、可用性、适配器安装和实际运行来源应统一且可追溯；历史脚本不构成新项目提供商切换方案。保留 ChatGPT/OpenAI 与 DeepSeek 配置及已安装切换器的当前用户偏好，不因旧项目用过 Qwen而擅改。

### 注释与行为不能互相替代

watch_ch3.py 顶部仍称“仅生成原始分复核待办，不改平台”，后文 auto_return/deliver 已包含平台写入。[S6:1,90–173] judge.grade_images 注释称温度 0 保证可复现，同文件 merge_votes 说明已观察到温度 0 的判分分歧。[S4:122,207–215]

**设计影响（研究判断）**：以实际调用路径及运行证据判断行为，文档“只读”“已复核”“可复现”等声明应有可核对事实支撑。

## 历史规则必须重新决定

| 议题 | 旧资料中的不同口径 | 对新设计的影响 |

| 分数范围 | 旧项目普遍硬编码/配置 75–98，并拒绝范围外最终分。[S6:56–58][S10:12–13][S12] | 这是旧课程政策，不是通用批改正确性条件。 |

本节是差异调查，尚未替用户锁定任何选项。

## 恢复能力的实际边界

1. **已有**：增量账本单文件先写临时文件再 replace；上传确认和待核验分开保存；失败留待重试；回传前重新读取提交版本；已定稿重交阻塞自动覆盖。[S6:25–30,138–173]
2. **未证明**：多个结果文件与平台写入之间的原子性。accept 顺次写学生 JSON、_final.json，再改内存状态；deliver 成功与 upload_ack 落盘之间存在中断窗口。重试同一得分可能是可容忍操作，但平台是否提供幂等约束、是否会产生其他副作用，本次没有验证。[S6:75–80,155–159]
3. **未证明**：回滚平台状态、恢复未交、跨进程互斥锁、批处理唯一执行权、冲突检测覆盖全部入口、无限名单分页、材料完整性校验、保留/清理政策。这些不能因有 state.json 就宣称完成。
4. **特别限制**：fingerprint 使用作业标识、学生标识、answerId、附件 objectid、提交时间，不包含附件字节、题目/参考答案/评分要点/提供商版本。它对历史附件提交有价值，但不是整个批改输入的完整版本指纹。[S6:19–22]

## 测试定义与未验证事实

旧仓库包含 emit_guard、judge_votes、roster、verify、watch_ch3 等测试。读取到的名称覆盖：缺题/非法分数、名单唯一性、只输出给分者、取整差异、人工平台差异、重交保护、上传失败重试、写前版本变化和完成证据。[S17]

本研究未执行这些测试，未评估全部断言质量，不声称当前测试通过，更不把 mock 测试当平台兼容性证明。

下列事项仍需后续研究或用户决策：

- 当前学习通账号/课程下实际界面、接口和状态语义；旧文档不是当前平台契约。
- 参考答案的文本/图片/附件形式、题目与答案缺失/错配、版本变化时如何处理。
- 纯文字、多附件、Word、图片和坏 PDF 的端到端覆盖；存在局部文字提示分支不代表通用链路支持。
- 模型准确性、不同题型误差、手写可读性、费用与速度、独立复核效果。本次未读取学生样本或做模型实验。
- 个人信息最小化、保存时长、教师权限与授权、错误回传后的纠正路径。
- 新项目首版范围及验收标准，应回到 HITL 决策票讨论。

## 建议后续决策顺序

这是研究建议，非已接受计划：

1. 先定首版工作流、题型/材料范围、教师介入点以及与学习通已有评分的边界。
2. 再定评分依据与版本、不可读/缺答案/不一致时的暂停和裁决规则。
3. 决定自动回传资格、幂等重试、平台人工改分冲突及回传后核验标准。
4. 最后用选定范围验证平台取数与写回，以及模型质量与运行成本；复用代码须经过这些边界下的测试。
